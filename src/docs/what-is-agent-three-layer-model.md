## 1. 什么是 Agent？

### 1.1 定义

**AI Agent（智能体）** 是一个能够**自主感知环境、做出决策、执行行动并从反馈中学习**的智能系统。它不仅仅是"回答问题"，而是能够**主动完成复杂任务**。

在 LLM 语境下，Agent 的核心定义可以概括为：

> **Agent = LLM + 工具 + 自主决策循环**

更具体地说，一个 Agent 系统通常包含以下关键能力：

| 能力 | 说明 |
|------|------|
| **感知（Perceive）** | 理解用户意图、读取环境状态、解析工具返回结果 |
| **推理（Reason）** | 分析问题、拆解任务、制定策略 |
| **规划（Plan）** | 确定行动步骤、选择合适工具、设定子目标 |
| **行动（Act）** | 调用工具、执行操作、与外部系统交互 |
| **反思（Reflect）** | 评估行动结果、从错误中学习、调整策略 |

### 1.2 Agent 的本质特征

一个真正的 Agent 区别于普通程序的关键特征：

```
┌─────────────────────────────────────────────────────────────┐
│                    Agent 的五大本质特征                        │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  1. 自主性（Autonomy）                                        │
│     └── 无需人类逐步指导，能独立决策和行动                      │
│                                                               │
│  2. 反应性（Reactivity）                                      │
│     └── 能感知环境变化并实时响应                               │
│                                                               │
│  3. 主动性（Pro-activeness）                                  │
│     └── 不仅被动响应，还能主动采取行动达成目标                  │
│                                                               │
│  4. 工具使用（Tool Use）                                      │
│     └── 能调用外部工具扩展自身能力边界                          │
│                                                               │
│  5. 持续学习（Learning）                                      │
│     └── 从交互中积累经验，持续改进表现                          │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

### 1.3 一个直观的类比

| 概念 | 类比 | 说明 |
|------|------|------|
| **普通 LLM 调用** | 图书馆咨询台 | 你问一个问题，它从知识库中给你答案 |
| **工作流** | 自动化流水线 | 按照预设流程，一步步完成固定任务 |
| **Agent** | 私人助理 | 理解你的目标，自主规划步骤，使用各种工具，遇到问题自己解决 |

## 2. Agent vs 普通 LLM 调用

### 2.1 核心区别

普通 LLM 调用和 Agent 之间的本质区别不在于"是否使用 LLM"，而在于**系统的控制权在谁手里**。

```
普通 LLM 调用：
  用户 ──问题──▶ LLM ──答案──▶ 用户
  └─ 人类控制整个流程，LLM 只是"回答机器"

Agent：
  用户 ──目标──▶ Agent ──自主执行──▶ 结果 ──▶ 用户
                    │
                    ├── 调用工具
                    ├── 分析反馈
                    ├── 调整策略
                    └── 循环迭代
  └─ Agent 控制执行过程，人类只需设定目标
```

### 2.2 详细对比表

| 维度 | 普通 LLM 调用 | Agent |
|------|--------------|-------|
| **交互模式** | 单轮问答 | 多轮自主交互 |
| **任务复杂度** | 简单到中等 | 复杂、多步骤 |
| **工具使用** | 无（或单次） | 多次、动态选择工具 |
| **决策权** | 用户完全控制 | Agent 自主决策 |
| **上下文管理** | 单次对话窗口 | 跨多轮持久化状态 |
| **错误处理** | 用户手动重试 | Agent 自动检测和恢复 |
| **执行时长** | 秒级 | 分钟到小时级 |
| **外部交互** | 无 | 可调用 API、数据库、文件系统等 |
| **记忆能力** | 仅当前对话 | 短期+长期记忆 |
| **规划能力** | 无 | 任务分解与规划 |

### 2.3 具体示例对比

**场景：帮我分析上个月的销售数据，找出下降原因，并生成改进建议报告**

#### 普通 LLM 调用方式：

```
用户: "帮我分析上个月的销售数据，找出下降原因，并生成改进建议报告"

LLM: "我无法访问你的销售数据。请你提供数据，我可以帮你分析。
      通常销售下降可能由以下原因导致：1. 季节性波动 2. 竞品活动
      3. 定价问题...建议你检查这几个方面。"

问题：LLM 只能给出通用建议，无法真正完成任务。
```

#### Agent 方式：

```
用户: "帮我分析上个月的销售数据，找出下降原因，并生成改进建议报告"

Agent 自主执行:
  Step 1: 调用数据库工具查询上月销售数据 → 获取 10000 条记录
  Step 2: 调用数据分析工具计算同比/环比 → 发现下降 15%
  Step 3: 按产品线、地区、渠道拆分分析 → 发现华东区下降 30%
  Step 4: 查询华东区市场活动记录 → 发现竞品同期做了大促
  Step 5: 综合分析，生成报告 → 输出包含数据图表和建议的 PDF

结果：Agent 真正完成了端到端的任务。
```

## 3. 三层演进模型

AI 应用从简单到复杂的演进可以归纳为三个层次。理解这个演进过程，有助于在合适的场景选择合适的技术方案。

```
┌─────────────────────────────────────────────────────────────┐
│                                                               │
│   第三层：Agent Loop                                          │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  LLM 自主决策循环，动态规划，持续迭代                    │   │
│   │  能力：自主规划 + 工具使用 + 错误恢复 + 长期记忆         │   │
│   └─────────────────────────────────────────────────────┘   │
│                          ▲                                    │
│                          │ 增加：自主决策、动态循环、记忆       │
│                          │                                    │
│   第二层：工作流（Workflow）                                   │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  预定义的 LLM 调用链，固定流程，确定性执行               │   │
│   │  能力：多步骤 + 条件分支 + 工具调用                      │   │
│   └─────────────────────────────────────────────────────┘   │
│                          ▲                                    │
│                          │ 增加：多步骤、工具、流程控制         │
│                          │                                    │
│   第一层：单次 LLM 调用                                       │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  一问一答，无状态，无工具，纯文本交互                    │   │
│   │  能力：理解 + 生成                                      │   │
│   └─────────────────────────────────────────────────────┘   │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 第一层：单次 LLM 调用

#### 3.1.1 架构

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│  用户输入  │────▶│   LLM    │────▶│  文本输出  │
└──────────┘     └──────────┘     └──────────┘

特点：一问一答，无状态，无外部交互
```

#### 3.1.2 核心特征

- **无状态**：每次调用独立，不记忆之前的对话（除非把历史放入 prompt）
- **无工具**：只能基于训练数据生成文本，无法访问外部信息
- **无自主性**：完全被动，用户问什么答什么
- **单轮决策**：一次调用完成，不会自我修正

#### 3.1.3 典型应用

| 应用 | 示例 |
|------|------|
| 文本分类 | "这封邮件是垃圾邮件吗？" |
| 摘要生成 | "帮我总结这篇文章" |
| 翻译 | "把这段中文翻译成英文" |
| 简单问答 | "什么是量子计算？" |
| 内容生成 | "写一封请假邮件" |

#### 3.1.4 增强手段

即使是单次调用，也可以通过以下方式增强效果：

```
基础调用：
  User Prompt → LLM → Response

增强调用：
  ┌─────────────────────────────────────┐
  │  System Prompt（角色设定）            │
  │  + Few-shot Examples（示例）          │
  │  + RAG Context（检索增强上下文）       │
  │  + User Prompt（用户输入）             │
  └─────────────────────────────────────┘
              ↓
            LLM
              ↓
          Response
```

- **System Prompt**：设定角色和行为边界
- **Few-shot Prompting**：提供示例引导输出格式
- **RAG（检索增强生成）**：注入外部知识弥补训练数据的局限
- **结构化输出**：要求 JSON/XML 等格式便于程序解析

#### 3.1.5 局限性

```
单次调用的天花板：

✗ 无法访问实时数据（数据库、API）
✗ 无法执行操作（发邮件、创建文件）
✗ 无法处理需要多步推理的复杂任务
✗ 无法从错误中自我修正
✗ 无法跨会话保持状态
```

### 3.2 第二层：工作流（Workflow）

#### 3.2.1 架构

```
┌──────────────────────────────────────────────────────────┐
│                      工作流引擎                            │
│                                                            │
│  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐ │
│  │ Step 1  │───▶│ Step 2  │───▶│ Step 3  │───▶│ Step 4  │ │
│  │ LLM调用  │    │ 工具调用 │    │ LLM调用  │    │ 汇总输出 │ │
│  └─────────┘    └─────────┘    └─────────┘    └─────────┘ │
│       │              │              │              │       │
│       ▼              ▼              ▼              ▼       │
│   代码控制        代码控制       代码控制       代码控制    │
│                                                            │
│  特点：流程由代码预定义，LLM 在固定节点被调用               │
└──────────────────────────────────────────────────────────┘
```

#### 3.2.2 核心特征

- **流程预定义**：步骤顺序由开发者用代码确定
- **确定性执行**：相同输入走相同路径
- **LLM 作为组件**：LLM 在特定节点被调用，不是全程自主
- **工具集成**：可以在步骤间调用外部工具
- **条件分支**：支持 if-else 逻辑（但分支条件也是预定义的）

#### 3.2.3 常见工作流模式

##### 模式 1：提示链（Prompt Chaining）

```
输入 → [LLM: 生成大纲] → [检查] → [LLM: 基于大纲写作] → 输出
```

将任务分解为顺序执行的子任务，前一步的输出作为后一步的输入。

**示例**：文档生成
```
Step 1: LLM 分析需求 → 生成文档大纲
Step 2: 程序检查大纲是否包含必要章节
Step 3: LLM 基于大纲逐章写作
Step 4: LLM 审校全文，修正错误
```

##### 模式 2：路由（Routing）

```
                    ┌→ [LLM: 退款处理]
输入 → [分类器] ────┼→ [LLM: 技术支持]
                    └→ [LLM: 一般咨询]
```

根据输入内容分类，路由到不同的处理分支。

**示例**：客服系统
```
用户: "我的订单还没到"
  → 分类器判断: 物流查询
  → 路由到: 物流查询工作流
  → 调用物流 API → LLM 生成回复

用户: "我要退款"
  → 分类器判断: 退款请求
  → 路由到: 退款处理工作流
  → 验证订单 → 执行退款 → LLM 生成确认
```

##### 模式 3：并行化（Parallelization）

```
         ┌→ [LLM: 语法检查] ──┐
输入 ────┼→ [LLM: 风格检查] ──┼→ [聚合] → 输出
         └→ [LLM: 事实核查] ──┘
```

多个 LLM 调用同时执行，结果汇总。

**示例**：代码审查
```
输入: 一段代码
  ├→ LLM-1: 检查安全漏洞
  ├→ LLM-2: 检查性能问题
  ├→ LLM-3: 检查代码风格
  └→ 汇总: 合并所有问题，生成审查报告
```

##### 模式 4：编排器-工作者（Orchestrator-Workers）

```
              ┌→ [Worker: 分析文件A]
编排器 ──────┼→ [Worker: 分析文件B]
              └→ [Worker: 分析文件C]
              ↓
          [编排器: 汇总结果]
```

一个中央 LLM 动态分解任务，分配给多个 Worker 执行。

##### 模式 5：评估器-优化器（Evaluator-Optimizer）

```
生成器 → 评估器 → 不合格？→ 反馈 → 生成器 → ...
                  ↓ 合格
                 输出
```

一个 LLM 生成，另一个 LLM 评估，循环直到满足标准。

#### 3.2.4 工作流的优势与局限

| 优势 | 局限 |
|------|------|
| ✅ 可预测、可调试 | ❌ 灵活性有限 |
| ✅ 流程透明、可审计 | ❌ 无法应对意外情况 |
| ✅ 成本可控 | ❌ 修改流程需要改代码 |
| ✅ 适合标准化业务 | ❌ 复杂任务难以预定义所有路径 |
| ✅ 易于测试和监控 | ❌ 步骤固定，无法动态优化 |

### 3.3 第三层：Agent Loop

#### 3.3.1 架构

```
┌─────────────────────────────────────────────────────────────┐
│                       Agent Loop                              │
│                                                               │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │                     ┌──────────┐                         │ │
│  │   用户目标 ────────▶│  Agent   │                         │ │
│  │                     │  Core    │                         │ │
│  │                     └────┬─────┘                         │ │
│  │                          │                               │ │
│  │         ┌────────────────┼────────────────┐              │ │
│  │         ▼                ▼                ▼              │ │
│  │   ┌──────────┐    ┌──────────┐    ┌──────────┐          │ │
│  │   │  Think   │───▶│   Act    │───▶│ Observe  │          │ │
│  │   │  思考     │    │  行动     │    │  观察     │          │ │
│  │   └──────────┘    └──────────┘    └──────────┘          │ │
│  │         ▲                              │                 │ │
│  │         └──────────────────────────────┘                 │ │
│  │                    循环直到目标达成                        │ │
│  └─────────────────────────────────────────────────────────┘ │
│                                                               │
│  特点：LLM 自主控制循环，动态决策，持续迭代                    │
└─────────────────────────────────────────────────────────────┘
```

#### 3.3.2 Agent Loop 的核心循环

Agent Loop 的本质是一个**自主的感知-思考-行动循环**：

```
while 目标未达成 and 未超过最大步数:
    1. Think（思考）
       - 分析当前状态
       - 回顾已完成步骤
       - 决定下一步做什么
       - 选择合适的工具

    2. Act（行动）
       - 调用选定的工具
       - 执行具体操作
       - 记录行动内容

    3. Observe（观察）
       - 获取行动结果
       - 评估是否接近目标
       - 检测是否有错误
       - 更新内部状态

    4. Decide（决策）
       - 目标已达成？→ 退出循环，返回结果
       - 遇到错误？→ 调整策略，继续循环
       - 需要更多信息？→ 继续循环
       - 超过最大步数？→ 返回部分结果
```

```

│  │   Planning   │   │  Tool Use   │   │   Memory    │        │
│  │   规划模块    │   │  工具使用    │   │   记忆模块   │        │
│  ├─────────────┤   ├─────────────┤   ├─────────────┤        │

│  │ • 优先级排序 │   │ • 参数构造   │   │ • 长期记忆   │        │

#### 3.3.4 Agent Loop 的完整执行示例

**任务：帮我研究 Python 和 Go 在微服务场景下的优劣，生成对比报告并发送邮件**

```
═══════════════════════════════════════════════════════════
第 1 轮循环
═══════════════════════════════════════════════════════════
Think:  这是一个研究+报告生成任务。我需要：
        1. 搜索 Python 微服务相关信息
        2. 搜索 Go 微服务相关信息
        3. 对比分析
        4. 生成报告
        5. 发送邮件
        先从搜索开始。

Act:    web_search("Python 微服务 性能 优缺点 2024")
Observe: 返回 10 条相关链接和摘要

═══════════════════════════════════════════════════════════
第 2 轮循环
═══════════════════════════════════════════════════════════
Think:  已获取 Python 相关信息。现在搜索 Go 的信息。

Act:    web_search("Go golang 微服务 性能 优缺点 2024")
Observe: 返回 10 条相关链接和摘要

═══════════════════════════════════════════════════════════
第 3 轮循环
═══════════════════════════════════════════════════════════
Think:  摘要信息不够详细，需要深入阅读几篇关键文章。

Act:    web_fetch(url="https://example.com/python-microservices")
Observe: 获取完整文章内容（约 3000 字）

#### 3.3.5 Agent Loop 的核心特征

| 特征 | 说明 |
|------|------|
| **自主决策** | LLM 决定每一步做什么，而非预定义流程 |
| **动态规划** | 根据中间结果实时调整计划 |
| **工具使用** | 自主选择和使用各种工具 |
| **错误恢复** | 遇到错误自动分析原因并重试 |
| **状态管理** | 维护跨步骤的上下文和状态 |
| **人机协作** | 在关键节点可以请求人类介入 |
| **循环迭代** | 持续执行直到目标达成或触发终止条件 |

#### 3.3.6 Agent Loop 的终止条件

Agent Loop 不能无限运行，需要明确的终止条件：

```
终止条件类型：

1. 目标达成
   └── Agent 判断任务已完成，主动退出

2. 最大步数限制
   └── 超过预设的最大循环次数（如 50 步）

3. 超时限制
   └── 总执行时间超过预设阈值（如 10 分钟）

4. Token 预算耗尽
   └── 累计消耗 token 超过预算

5. 用户中断
   └── 用户手动停止执行

6. 错误不可恢复
   └── 遇到无法自动处理的致命错误

7. 人工审核点
   └── 到达预设的需要人工确认的检查点
```

## 4. 三层模型对比总结

### 4.1 核心维度对比

| 维度 | 单次 LLM 调用 | 工作流 | Agent Loop |
|------|:-----------:|:-----:|:----------:|
| **复杂度** | ⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **自主性** | 无 | 低 | 高 |
| **灵活性** | 低 | 中 | 高 |
| **可预测性** | 高 | 高 | 低 |
| **开发难度** | ⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **调试难度** | ⭐ | ⭐⭐ | ⭐⭐⭐⭐⭐ |
| **成本** | 低 | 中 | 高 |
| **延迟** | 秒级 | 秒~分钟 | 分钟~小时 |
| **错误处理** | 无 | 预定义 | 自主恢复 |
| **工具使用** | 无/单次 | 预定义 | 动态选择 |
| **适用任务** | 简单问答 | 标准化流程 | 复杂开放式 |

### 4.4 同一任务在三层模型中的表现

**任务：分析一个 GitHub Issue 并尝试修复**

| 层次 | 处理方式 | 结果 |
|------|----------|------|
| **单次调用** | 用户把 Issue 内容贴给 LLM，LLM 给出可能的修复建议 | 只能给建议，无法真正修复 |
| **工作流** | Step1: 读取 Issue → Step2: 搜索相关代码 → Step3: LLM 分析 → Step4: 生成 patch | 能生成 patch，但流程固定 |
| **Agent** | 自主读取 Issue → 搜索代码库 → 理解上下文 → 定位问题 → 尝试修复 → 运行测试 → 测试失败 → 分析原因 → 修改方案 → 再次测试 → 通过 → 提交 PR | 端到端自主完成 |

## 5. 从理论到实践：何时升级

### 5.1 升级决策框架

```
当前方案是否满足需求？
├── 是 → 保持当前层次，不要过度设计
│
└── 否 → 分析瓶颈在哪里：
    ├── LLM 知识不足？→ 单次调用 + RAG
    ├── 需要多步骤？→ 升级到工作流
    ├── 需要访问外部系统？→ 工作流 + 工具集成
    ├── 流程太死板？→ 升级到 Agent Loop
    ├── 需要自主决策？→ 升级到 Agent Loop
    └── 需要错误恢复？→ 升级到 Agent Loop
```

### 5.2 实践原则

1. **从最简单开始**
   - 永远先尝试单次 LLM 调用 + 优化 prompt
   - 很多问题通过好的 prompt 工程就能解决

2. **渐进式升级**
   - 单次调用不够 → 加 RAG
   - RAG 不够 → 加工作流
   - 工作流不够 → 考虑 Agent

3. **成本意识**
   - Agent Loop 的 token 消耗可能是单次调用的 10-100 倍
   - 确保增加的复杂性带来对应的价值

4. **安全边界**
   - Agent 越自主，安全措施越重要
   - 设置明确的权限边界和人工审核点

5. **可观测性**
   - 每一层都需要日志和监控
   - Agent 层尤其需要记录每一步的推理过程

### 5.3 总结

```
┌─────────────────────────────────────────────────────────────┐
│                                                               │
│   核心认知：Agent 不是魔法，而是 LLM 能力的工程化延伸          │
│                                                               │
│   单次调用 → 工作流 → Agent Loop                              │
│   从"回答问题"到"执行流程"再到"自主完成任务"                   │
│                                                               │
│   关键不是追求最高层次，而是找到最适合当前问题的那一层          │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```
